## 0. 一页结论

**三条最重要的判断：**

1. **代价函数的价值 99% 在"门"（排除坏对），不在"序"（排列好对）。**
   A2 实测：便宜池内"代价最优 / 最差 / 随机"三种取法的损伤差异 **≤12%**，
   **小于随机抽样离散度 39%**，`Spearman(代价, 实测损伤) = −0.002`。
   所有"更好的排序"类改进必然撞墙。

2. **候选图的 Oracle 天花板是 1.09×**，折算端到端 ≈ 0.01 dB。
   三条完全不同的改法（加 K、多线索、尺度归一化）收敛到同一上限。

3. **唯一稳定有效的是 p2c1（几何+颜色门控）**：三场景 +0.075/+0.158/+0.043 dB。
   E4 守卫（+0.017/+0.074/+0.025）为次优；其余 12 类改动全部证否或低于噪声。

**Oracle → 端到端的折算率：约 8–10 倍**（三次独立复现）。

## 2. 收获 A：方法层面的可靠结论

### 2.1 代价函数是"门"不是"序"（A2，最强结论；2026-11-16 修正版）

> 初版随机臂有 bug（`argsort` 的下标被当成边 id，四种子的选择完全相同），
> ROI 掩码也误用了单视角。修正后见 `REPORT-audit-code.md`。

| 取法（同一便宜池，K=500） | ROI 损伤 |
|---|---:|
| 代价最优 | 2.414e-05 |
| 代价最差 | 2.203e-05 |
| 随机（4 次均值） | 2.150e-05 |
| 随机抽样离散度 | **39.3%** |

`best/random = 1.123`、`worst/best = 0.913`、`Spearman = −0.002`；
三种取法的差异（≤12%）**小于抽样本身的离散度（39%）**。
**→ 池内的对本来就都无害，最优/最差/随机统计上不可区分。**

### 2.2 排序的"总价值"几乎全部由"用任何距离型代价"兑现

> **重要更正（2026-11-16）**：先前在本文 §8 与 `REPORT-rho-curve.md` §3 里写过
> "高压缩比下排序有 2 dB 空间、我们只兑现 0.1 dB"——**这是把两个不同参照物混用了**。
> 2 dB 是"随机 vs p2c1"，而 0.1 dB 是"p2c1 vs scale_norm"。拆开后结论完全相反。

三档同预算、同指标（PSNR vs GT）、同最终高斯数的完整分解：

| ρ | 随机 | **scale_norm**（仅几何） | p2c1 | 随机→scale_norm | scale_norm→p2c1 |
|---|---:|---:|---:|---:|---:|
| 0.02 | 16.7690 | 18.7293 | 18.8317 | **+1.960** | +0.102 |
| 0.05 | 18.1112 | 20.0695 | 20.0242 | **+1.958** | −0.045 |
| 0.10 | 19.3682 | 21.0653 | 21.1399 | **+1.697** | +0.075 |
| 0.20 | 21.0578 | —（未测） | 22.2875 | — | — |
| 0.50 | 23.5999 | —（未测） | 23.6205 | — | — |

**读数**：
- "排序价值"（随机→p2c1）在 ρ=0.02 是 +2.06 dB，但其中 **+1.96 来自"用了任何距离型代价"
  （哪怕是最朴素的 scale_norm），只有 +0.10 来自 p2c1 这个精修**；
- 三档的分配比一致：scale_norm 吃掉 **96%–102%**，p2c1 的边际始终在 ±0.1 dB；
- 所以**不存在"高压缩比下多出 2 dB 可挖"**——那 2 dB 是 scale_norm 的功劳，早已计入主结果。

**正确的表述**：压缩比越强，"用一个合理代价"越重要（0.02 dB → 2.06 dB），
但**合理代价一旦确定，其内部的排序精修在任何压缩比下都只有 0.1 dB 量级**。

| 可见性/PUP | 2.07–2.17× | +0.006 dB |

**筛选用门槛：Oracle < 1.5× 不可能产生可测收益。**

| 对比 | 全图 | edge ROI | **tex ROI** | LPIPSe |
|---|---:|---:|---:|---:|
| p2c1 − scale_norm（garden） | +0.055 | +0.065 | **+0.087** | −0.0036 |

### 2.6 管线没有"按细节分配密度"

体素分区统计（truck 233 区）：**所有细节分位的合并比例都是 ≈48.5%**，
p2c1 相对 scale_norm 的重分配仅 **±0.15%**。
**→ p2c1 不是靠"把合并挪出细节区"获益，而是在同一区域内挑到更好的对。**

**复核补正（2026-11-16，`REPORT-pics-e2e.md` §7/§8）——本轮最重要的发现不是相机，是 `--sh-clip`：**

所有 suite 脚本都用 `--sh-mode dc --sh-sum 1 --sh-min-diff 0.2` 而未给 `--sh-clip`，于是落到默认 **0.30**；
但 `REPORT-sh-free.md` 推荐的是 **0.05**，`REPORT-sh-correction.md` 把 0.3 列为"超参太猛"的失败项。
实测（fast 臂，只改 clip）：

| 场景 | clip 0.30（历史/当前默认） | clip 0.05（推荐） | Δ |
|---|---:|---:|---:|
| truck | 21.1243 | 21.3632 | **+0.239** |
| room | 26.2347 | 27.0614 | **+0.827** |
| garden | 21.3479 | 22.1133 | **+0.765** |
| bicycle | 20.6589 | 20.8350 | **+0.176** |

clip 扫描（truck/room）：0.02 → 21.333 / 27.073；0.05 → 21.363 / 27.061；0.10 → 21.379 / 26.978；
0.20 → 21.302 / 26.653；0.30 → 21.124 / 26.235。**最优区间 0.02–0.10，0.30 越过悬崖（比不校正还差）。**

在 clip=0.05 下，相机采样 **四场景全正**：truck +0.178（guard）/ +0.191（cover）、room +0.229 / +0.218、
garden +0.063 / +0.057、bicycle +0.122 / +0.198。上一轮记录的 garden −0.125、bicycle −0.162 **完全是 clip=0.30 造成的**。
`E_alpha` 的方向也随之与端到端一致。教训：**消融必须在调好的超参下做**；本表其余条目（p2c1 等主结果）
同样是在 clip=0.30 下测的，可能被系统性低估 0.2–0.8 dB，建议按 clip=0.05 复核。


**另一个参照点（关掉 SH 校正，`--sh-mode s0`）**：
truck fast 21.3045 → guard 21.4818（**+0.177**）；garden 21.9579 → guard 22.0542 / track 22.0332（**+0.096 / +0.075**）；
bicycle 20.6888 → guard 20.8581（**+0.169**）。即**透明度层面的相机收益在 4/4 场景成立**，
dc 下的负号（garden −0.125、bicycle −0.162）正好等于两臂的 SH 代价之差（0.22/0.33 dB）。
实现正确性另有四项验证：同一视角集走 PICS 内核 vs 生产内核差 **4×10⁻⁵ dB**；
逐 pair 路由 max 差 **6×10⁻⁸**；离线排序在 **10 万 pair**（12× pilot）上不变；跨 GPU 逐位一致。
仍未查清：SH 增量与不同透明度场的相互作用（已排除"SH 求和随视角集变化"）。
**判定（主配置 dc）：不采纳为默认。** 机理完全达到（零支撑归零、`E_alpha` 降 3–10 倍），但 4 场景 2 正 2 负，
且**离线最优的 track 端到端最差**。关键负结果：
① `E_alpha` 与端到端在 garden/bicycle 上**反向**（garden：0.252→0.027 但 PSNR −0.219），
说明"逼近全相机 O2cal 解"不是正确的优化目标；
② `guard` 的隔离实验显示 garden 上 **fallback `a0` 比任何拟合 α 都好**（只改 17.3% 的 pair 仍 −0.125 dB），
bicycle 同理（−0.162）；轨迹图显示修复会把边缘 pair 的视角拉到轨迹**对侧**。
下一步建议：两维场景门（平均支撑数 + track overlap → 决定是否开 guard）+ 去相关加权估计量。

## 8. 结论与建议

**已确立的（可写进结论）：**
1. p2c1 三场景稳定 +0.04~0.16 dB，成本 +0.09 s；
2. E4 守卫三场景 +0.017~0.074 dB，成本 +0.03 s；
3. 提速包 −3~11%（truck −11%），画质损失 ≤0.002 dB；
4. 方法论：代价是"门"不是"序"；Oracle 折算率 8–10 倍；误差集中在纹理 ROI。

**不建议再做的：**
- 任何"更好的排序/相似度"类特征（6 类全否）；
- 扩大候选图（天花板 1.09×）；
- 区域配额、跨轮继承、冗余度（上限 −2.9% / 无效果 / 0.96）。

**还剩的真正机会：**
1. **高压缩比区间**（ρ=0.02–0.05）：这里"有一个合理代价"比低压缩比更重要
   （+2.06 vs +0.02 dB），但**这份价值已由 scale_norm/p2c1 拿到**；
   在其之上 p2c1 的边际仍只有 +0.10 dB（见 §2.2 的更正）。
   若要再挖，只能寄望于**非逐对**的新准则——本轮所有逐对准则都已失败，
   且 A2 证明池内排序无关，所以这条路必须先证明"池本身可被换掉"；
2. **恢复侧**：`o2` 0.42 s 的网格/σ_cut 从未系统扫描；SH 校正仍有 +0.05 dB 免费收益；
3. **`mpmm` 0.552 s** 的矩阵运算优化（纯计算，未动过）。
