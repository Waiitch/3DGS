## 一、Stage 1：单份张量对齐审计（truck，pass-1 batch-0）

**严格按方案执行**：一次 `G_def` 运行内导出输入张量，再在独立脚本里对**完全相同**的张量分别跑两条路径，彻底消除上一轮的批次错位。

| 指标 | 实测 |
|---|---|
| `valid` 占比 / `ok(den>0)` | 52.26% / 136932 |
| **对齐后单视角 MAE** | **0.01905**（有符号 +0.00991） |
| κ ∈ [0,2) | n=36143，MAE **0.00855** |
| κ ∈ [2,5) | n=72499，MAE **0.01291** |
| κ ∈ [5,∞) | n=27977，MAE **0.04853** |
| `c_ijm` **非有限值** | **2273 / 262144** |
| `c_im` / `c_jm` 最大值 | **7.3e42 / 6.5e41**（理论界 ≤ 2） |
| 坏点 `Σ_m` 的最大特征值 | 中位 **3.8e41**、max **8.2e45** |
| `lmax>1e6` 的溢出视角占比 | 0.2286%（313 / 136932） |

**结论**：上一轮报告里"单视角 MAE 0.315"是批次错位的工件。真实单视角误差只有 **0.019**，误差随偏心率单调上升（0.0086 → 0.0485），与短轴欠采样一致，但**幅度很小**。

## 二、根因：NaN 穿透 `valid` 并毒化轮级校准

1. 近平面退化投影使 `Σ_m` 达 **1e41–1e45**；
2. 手写 2×2 求逆的 `det = a*c − b*b` 在 Float64 下发生灾难性抵消 → `c_ijm` 爆到 **1e9** 或 **NaN**（2273 个），`c_im` 爆到 **1e42**；
3. 内核里 `am = torch.where(torch.isfinite(am), am, a0)` 把 **NaN 替换成 `a0`（≈1.0）**，而正常 α 只有 ~0.85；
4. 于是 `am_mean_pre_cal` 被抬高（truck 0.8238 → 0.8462、room 0.8875 → 0.9001）；
5. 轮级校准 `f_cal = a0.mean() / am.mean()` 因此变小 → **全局 α 被整体压低约 4%** → 所有正常 pair 一起受损。

**方案 §1.2 的判断完全正确**：哪怕 0.2% 的视角爆离群，也足以通过 `cal` 拉偏整轮。

## 三、修复：只需一个 NaN 防护

在 `o2_closed_form_batch` 中加入（永远生效，不引入任何新超参）：

```python
bad_v = ~torch.isfinite(alpha_v)          # 非有限值 → 权重置 0 并从掩码剔除
alpha_v = where(bad_v, 0, alpha_v)
c_im/c_jm/c_ijm = nan_to_num(..., nan=0, posinf=0, neginf=0)
m_f = m_f * (~bad_v)
```

**没有使用** Fix 1（安全阀）/ Fix 3（`ecc_floor`）：实测不需要，而且我实现的 Fix 1+2 组合**有 bug**（见 §6）。

## 六、必须记录的实现缺陷

`--o2-cf-safe` / `--o2-cf-fix`（方案 Fix 1 + Fix 2）**实现有 bug**：启用后 `am_mean` 爆到 **2.7e5**、PSNR 掉到 **4.87 / 8.69**。原因是我把"退化协方差掩码"与"c 上界 clamp"组合时引入了新的传播路径错误（`alpha_v` 在 clamp 前已被判为 bad 但随后又被重算，掩码与重算结果不自洽），具体点尚未定位。

**处置**：两个开关的 help 文本已改为 `BROKEN, do not use`，默认关闭；**核心 NaN 防护单独即可达成全部收益，且不动任何合法 pair**。

## 六b、gather 优化（只对有效 pair-view 求值）

**改动**：闭式解原本在完整 `(B, V)` 张量上求值，而网格路径早已 `nonzero(ok)` 只处理有效视角。现已对齐：gather → 闭式解 → `index_add_` 散射聚合，逐 pair 权重逻辑完全不变。

**正确性**：7/7 场景 PSNR **逐位不变**

| 场景 | 优化前 PSNR | 优化后 PSNR |
|---|---|---|
| truck | 21.543603897094727 | **21.543603897094727** |
| room | 27.374937057495117 | **27.374937057495117** |
| garden | 22.09965705871582 | **22.09965705871582** |
| bicycle | 21.035669326782227 | **21.035669326782227** |
| playroom | 28.617891311645508 | **28.617891311645508** |
| train | 17.976627349853516 | **17.976627349853516** |
| drjohnson | 27.329683303833008 | **27.329683303833008** |

**性能**：`o2_cf` 阶段每 batch 从 **~8.7 ms 降到 ~6.5 ms（−25%）**，且各场景的每 batch 成本从"2.5–8.8 ms 不稳定"收敛为"5.8–7.2 ms 一致"。

**但 −25% 远小于有效视角占比所暗示的 −60~77%**（truck 有效 43%、train 56%、playroom 23%）。这说明闭式解**不是元素数受限，而是逐元素 kernel 发射数受限**：每个 batch 约 50 个独立 fp64 张量操作，在共享 GPU 上每次发射的延迟被放大。实测佐证：同形状微基准（`bench_o2_cf.py`，B=32768/V=8）在 playroom / room / bicycle 三个完全不同的数据上都是 **6.6 ms，比值 1.00×** —— 与元素内容、甚至与有效视角数无关。

**结论**：gather 保留（严格少做工作且逐位等价），但若继续追求速度，唯一有效的方向是**算子融合**（把 ~50 次发射合并成 1–3 个融合核），而不是继续减少元素数。
