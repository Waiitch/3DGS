### 2.2 逐场景读数

**truck**：所有"修支撑"的臂都落在 +0.15~+0.17 区间，彼此差 0.02 dB（≈ 该评测器的分辨下限）。
cover 仍在最前；pair-conditioned 的 B=6/8/12 没有单调性（+0.149/+0.152/+0.158）→ **B>6 的部分是噪声**。

**room**：唯一一个"pair-conditioned 超过 cover"的案例：**repair6 +0.182 > guard8 +0.164 > cover +0.157**。
但同一规则在 B=8/12 反而退化（+0.122/+0.081）。room 的 8 视角平均只有 2.36 个有效支撑，
扩到 ~5 个有效视角时最好，继续加就引入偏置观测。

**garden**：fast8 是**唯一正解**，任何改动都掉点，且改得越多掉得越多：
guard8 −0.125 → cover −0.148 → repair8 −0.176 → pref8 −0.198 → track −0.199/−0.219。

其中 `guard8` 最值得注意：它**只改动了 fast8 完全无支撑的那 17.3% 的 pair**
（其余 82.7% 的视角集与 fast8 逐位相同；实测 screen 判据下无支撑比例 truck/room/garden/bicycle = 18.9/15.3/17.3/21.2%），
仍然掉 **−0.125 dB**。也就是说：

> **在 garden 上，把"零支撑 pair"从 `a0 = α_i+α_j−α_iα_j` 换成一个真正拟合出来的 α，
> 反而更差。** fallback 不是缺陷，而是该场景下更好的估计量（§4.4）。

**bicycle**：同一现象的最强证据——零支撑比例最高（21.1%），`guard` 只碰这 21%，
PSNR 就掉 **−0.162 dB**（SSIM/ΔLPIPS 也同步变差）。这与历史 S5 的 bicycle −0.261（E4+cover）
方向一致：bicycle 也是对"改相机/改配对"最敏感的场景。

这条把方案的核心前提（"18–21% 走 fallback 是缺陷"）限定在了 truck/room 类场景。

## 3. 耗时

### 3.1 端到端（同机同配置、3 次重复、无并发负载的中位数）

|---|---:|---:|---:|---:|
| truck | **5.014 s**（O2 0.420） | 5.477 s (+9.2%) | **5.246 s (+4.6%)** | 5.475 s (+9.2%) |
| room | **3.550 s**（O2 0.220） | 3.980 s (+12.1%) | **3.832 s (+7.9%)** | 4.005 s (+12.8%) |
| garden | **9.977 s**（O2 0.928） | 10.281 s (+3.0%) | **10.471 s (+4.9%)** | 10.807 s (+8.3%) |

- `guard8` 三场景 **+4.6% / +7.9% / +4.9%**、bicycle **+8.8%**：贴近方案 §20.3 的 5% 目标；
- `repair8` **+8.3~12.8%**：超出 5% 目标，truck/room 超 10% 硬上限；
- `track` 最贵：truck +20%(B=6)/+33%(B=8)、room +17%/+22%、garden +19%/+20%（并发评测下的值，
  偏大，未单独做干净复测）——它每个 pair 要用满 5.7–7.8 个有效视角，是 fast8 的 2–2.5 倍；
- `cover` 的额外耗时几乎全部是一次性的 `pick_cover_views` 贪心（0.28–0.58 s，历史报告称可缓存到 ≈0），
  而 PICS 的一次性开销（全池解析 + `CamPool` + track overlap）只有 **0.05 s / 0.25–0.83 s**。

> 早期并发评测时测到的 +22~28% 是受干扰的值，以本表为准。
> O2 子阶段本身：fast 0.42/0.22/0.93 s → guard 0.67/0.42/1.47 s（1.6–1.9×）→ repair8 0.87/0.68/2.19 s（2.1–3.1×）。

### 3.2 成本构成，以及能压到多少

| 项 | 实测 | 说明 |
|---|---:|---|
| 每轮粗筛（全池 × 所有 pair） | 22–55 ms | 与 pair 数成正比，便宜 |
| 选视角（8–12 次 (P,V) 归约） | 30–240 ms | `repair` 每轮对 8 个 bin 各做一次 max |
| 精确 patch（pair × 已选视角） | 主项 | truck pass-1 0.43 s（fast8 是 0.25 s，1.7×） |
| 一次性：全池相机解析 + CamPool | 0.05 s（修好后） | 见下 |

**踩坑（值得写进文档）**：第一版把 `CamPool` 里的相机中心写成 `R.transpose(1,2) @ t`，
无意中初始化了 cuBLAS，触发 ~0.73 s 的一次性开销（管线全程 `--no-blas 1` 就是为了避免它）。
改成逐元素乘加后降到 **0.002 s**，JSON 里 `o2_cams` 从 0.73 s → 0.05 s。
这是"看上去像算法开销、实际是库冷启动"的典型案例。

**剩下的成本**是纯粹的浮点工作量：`repair` 平均每 pair 参与拟合的有效视角从 3.1 涨到 5.2（truck）
/ 6.5（room），而 grid 采样量正比于这个数。要压到 1.3× 只能减小 B（B=4 → 3.3 视角 ≈1.07×），
但 §2.1/离线表显示 B=4 的 `E_alpha` 已经明显变差（truck 0.0525 vs 0.0386）。

## 4. 机理：为什么"修好了支撑"却没有换来画质

### 4.1 `E_alpha` 与端到端在 garden/bicycle 上反向

| garden | fast8 | cover8 | repair8 | pref8 | **track8** |
|---|---:|---:|---:|---:|---:|
| `E_alpha`（对全相机 O2cal 解） | 0.2515 | 0.0734 | 0.0650 | 0.0511 | **0.0273** |
| 零支撑比例 | 17.2% | 0.4% | 0.4% | 0.4% | 0.4% |
| **PSNR** | **21.3479** | 21.2002 | 21.1723 | 21.1501 | **21.1290** |

| bicycle | fast8 | cover8 | guard8 |
|---|---:|---:|---:|
| 零支撑比例（fast8） | 21.1% | 3.1% | 0.0% |
| **PSNR** | **20.6589** | — | 20.4970 |

离线指标说 track 最好（`E_alpha` 比 fast8 低 **9 倍**），端到端说 track 最差（−0.219 dB）；
在 bicycle 上只修那 21% 的零支撑 pair，也是 −0.162 dB。
**在 garden / bicycle 上，"更接近全相机 O2cal 解"与"渲染质量"是反向的。**

这说明方案 §13.3 的隐含假设（`a_p^all` 是"更好"的目标）在两个场景上不成立：
全相机解本身按"屏幕覆盖 ≈ 源覆盖之和"求 α，而这个代理在
密集弧线相机 + 强遮挡（garden）与稀疏环绕（bicycle）场景里系统性偏离渲染器真正需要的 α。
8 个等间隔视角恰好把这种偏离落在一个可用的位置（每轮的 `f = mean(a0)/mean(am)` 标定又吸收一部分）。

**更精确的说法**（图 `figs/cam_support_garden.png` 直接可见）：对场景边缘的 pair，
修复把视角拉到了轨迹的**另一侧**——修出来的观测方向与渲染时真正看见它的方向系统性不同，
所以补得越多、错得越多。

### 4.2 为什么 cover 在 truck/room 有效、在 garden 失效

- truck/room 的相机基线宽（164/204 个 fit 视角，环绕完整），8 视角里只有 2.4–3.1 个有效；
  "补到 5–6 个有效视角"确实降低了 α 估计的方差，所以 +0.15~0.16 dB 是**方差收益**。
- garden 的相机是一条紧致弧（120 个 fit 视角扫过很短一段轨迹），8 个等间隔视角本身就
  近似"轨迹分层抽样"；贪心覆盖会挑**相邻机位**（历史：索引 2,4,7,11,14,15,17,20），
  这些视角的观测高度相关，加权后等价于"少数几个视角的均值"，反而放大相关性带来的偏置。
- 因此 garden 的正确方向不是"补更多视角"，而是**降低相关性**（相距更远的机位）
  或**改变估计量**（不是等权累加）。

### 4.3 B 的单调性并不存在

truck 上 B=6/8/12 是 +0.149/+0.152/+0.158，room 上是 +0.182/+0.122/+0.081，
garden 上 B=8/12 是 −0.176/−0.182。**同一预算在不同场景给出相反的排序**，
说明"每个 pair 多给几个视角"不是可迁移的杠杆——与 §4.1 一致：
问题不在"观测够不够"，而在"观测对不对"。

### 4.4 garden 的 fallback 是"对的"

`guard` 的隔离实验（只动 17.3% 的零支撑 pair、其余逐位不变）给出 −0.125 dB，
说明这些 pair 用 `a0 = α_i + α_j − α_i α_j` 比用任何拟合 α 都好。为什么？

`a0` 是"两个源高斯不透明时的透射率并集"，只依赖 pair 自己的两个 α，
不引入任何**别的视角**的覆盖假设。而 garden 是密集弧线相机 + 强遮挡：
真正看见这些 pair 的少数视角往往是掠射/强遮挡视角，
它们测到的"合并后屏幕覆盖"与渲染器实际合成的覆盖差得最远。
换句话说，**在 garden 上"看不见"比"看错了"更安全**——
这正是历史相机采样报告 §4 第 4 条的观察（"真实相机的缺陷是少看而不是看错"），
本轮把它从"18% 无观测"细化成了"这 18% 用 fallback 更好"。

由此得到一条可操作的规则（下一轮可直接验证）：

```
if  场景的"轨迹长度 / 相机数"很小（轨迹密集、baseline 窄，如 garden） -> 保留 fast8 + a0 fallback
else（轨迹覆盖宽，如 truck/room）                                    -> 修零支撑（guard）稳赚 +0.16 dB
```

场景判据可以用现成量：fit 相机中心的轨迹长度 / 相机数、或相邻相机的平均 track overlap。
两者都不需要 GT、不需要渲染，成本≈0。

## 6. 建议

1. **不要把 pair-conditioned 采样设为默认。** 机理正确、`E_alpha` 正确，但 4 场景里 2 正 2 负，
   且离线最优的 track 判据端到端最差。
2. **唯一值得保留的变体仍是 `guard`**（只在 fast8 完全无支撑时才修复）：
   truck +0.156 / room +0.164 / garden −0.125 / bicycle −0.162，端到端 **+4.6~8.8%**。
   它只在"相机基线宽、遮挡轻"的场景（truck/room）该开，在 camera-arc 密集或稀疏环绕的
   场景（garden/bicycle）必须关掉。
3. **场景门是下一步唯一有意义的工作**：判据用现成量（fit 相机轨迹长度/相机数、
   相邻相机平均 track overlap、8 视角平均支撑数），成本≈0；规则：
   `if 平均支撑数 > 3 且 track overlap 中位数 < 0.06 -> 开 guard，否则用 fast8`。
   truck/room 的平均支撑 3.08/2.36 与 garden/bicycle 的 2.88/1.73 在这个方向上不可分，
   所以要联合两个量（本轮数据可以直接拟合一个两维门限）。
4. **相机这条线真正剩下的问题是"估计量对不对"**，不是"选哪些相机"：
   - garden/bicycle 上应验证**去相关加权**（按 track overlap / 视角夹角加权，等价于广义最小二乘）；
   - 或给每个 pair 估计"视角间差异"并把偏离主流的视角降权。
   这两个方向都能从本轮已有的 `M`（track overlap）和 `E_alpha` 数据直接起步。
5. **离线指标的定位要写清楚**：`E_alpha` 只用于筛掉"明显没修好"的方案
   （它确实能识别 18.6/14.8/17.2/21.1% 零支撑 → 0%），**不能用于在"都修好了"的方案之间排序**——
   它甚至在 garden/bicycle 上与端到端反向。下一轮必须先建立"离线指标 → 端到端"的校准。

## 7. 复核：离线/在线不符是真实的吗？（2026-11-16 追加）

被问到"这是实际情况还是代码写错"，下面四项验证用来把"实现正确性"与"结论正确性"分开。

### 7.1 实现正确性：四项验证全部通过

| 编号 | 验证 | 结果 |
|---|---|---|
| V1 | 把 **garden cover8 的同一组相机**喂给 PICS 内核（`--o2-pick fixed`），与生产内核 `--o2-cams cover` 对比 | **21.200134 vs 21.200172**，差 **4×10⁻⁵ dB**；SSIM/LPIPS 差在 10⁻⁵ 量级 → 内核、per-view SH 累加、标定、clamp 全部等价 |
| V2 | **每对 pair 用不同相机**（64 pair × 4 台，各不相同），与"逐 pair 单独跑参考内核"对比 | max\|Δ\| **5.96×10⁻⁸**；行置换对照给出 7×10⁻² 的差异 → pid↔pair 路由正确，对照非空 |
| V3 | 离线指标在 **10 万 pair**（12× pilot）上重算 garden | fast 0.2481 / cover 0.0710 / repair 0.0645 / pref 0.0509 —— 与 8192 pilot 的排序完全一致（0.2515/0.0734/0.0650/0.0511）→ 不是抽样偶然 |
| V4 | 端到端确定性 | 同一臂在 4080/3090 两张卡上重复运行，PSNR 逐位相同（21.2767391204834 两次） |

**结论：管线、内核、路由、SH 累加都没有错。** 因此差异只能来自"选了哪些视角"以及**视角集对其它模块的连带影响**。

### 7.2 结论正确性：我上一轮的结论是错的

把 DC SH 校正关掉（`--sh-mode s0`）后重跑同样几个臂：

| 场景 | arm | dc（主配置） | s0（无 SH 校正） | SH 代价 | guard−fast：dc / s0 |
|---|---|---:|---:|---:|---:|
| truck | fast / guard | 21.1243 / 21.2803 | 21.3045 / 21.4818 | −0.180 / −0.202 | **+0.156 / +0.177** |
| garden | fast / guard | 21.3479 / 21.2226 | 21.9579 / 22.0542 | −0.610 / −0.832 | **−0.125 / +0.096** |
| garden | track | 21.1290 | 22.0332 | −0.904 | **−0.219 / +0.075** |
| bicycle | fast / guard | 20.6589 / 20.4970 | 20.6888 / 20.8581 | −0.030 / −0.361 | **−0.162 / +0.169** |

- **在 s0 下，pair-conditioned（guard）在四个场景全部为正**（+0.177 / +0.096 / +0.169，room 在 dc 下 +0.164），
  与离线 `E_alpha` 的方向一致。**"离线指标与端到端反相关"这个结论不成立**——
  它只在 dc 配置下成立，那是"透明度 + SH 校正"两个变量一起变的结果。
- 维度上：garden 的 −0.125 与 +0.096 之间正好是 0.221 dB，等于两个臂的 SH 代价之差（0.222）。
  bicycle 同理（0.331 ≈ 0.162+0.169）。**dc 配置下 pair-conditioned 的负号，全部可归因于 SH 校正这一项。**

### 7.3 机理仍未完全查清（诚实记录）

第一假设是"SH 的逐视角权重 `S_i=Σ_v a_i/√det_i` 沿用了拟合视角，换相机集就改了颜色校正"。**该假设被实验否掉**：

- V6：把 SH 求和改为固定累加在 fast8 参考视角上（`--o2-sh-ref fast`），garden guard 的 PSNR
  **21.222618 —— 与耦合版逐位相同**，说明 `S_i/S_j` 对视角集几乎不敏感；
- 直接测：`r=S_i/(S_i+S_j)` 在 fast8 与 top-6 视角集之间只变 **0.037（p90 0.092）**。

所以耦合不在 SH 的**权重**上。剩下的可能是"SH 的固定颜色增量与不同的透明度场在渲染中相互作用"
（即当前 `--sh-clip/--sh-lam/--sh-min-diff` 是与 fast8 的透明度**共同标定**的），
这一条**尚未被隔离验证**，属于本轮未解决的问题。能判定它的实验：
在 s0 透明度场下重算 SH 增量、或按臂扫描 `--sh-min-diff/--sh-clip`。

### 7.4 修订后的判定

| 项 | 修订前 | 修订后 |
|---|---|---|
| 管线实现 | — | ✅ 四项验证通过（4×10⁻⁵ dB / 6×10⁻⁸ / 12× pilot 稳定 / 跨卡逐位一致） |
| 离线 `E_alpha` 方向 | "与端到端反相关，不可用" | ⚠️ **在 s0 下与端到端同向**；在 dc 下被 SH 项掩盖，不能据此否定该指标 |
| pair-conditioned 是否有效 | "不建议采纳" | ⚠️ **透明度层面 4/4 场景有效**（+0.08~+0.18 dB）；dc 配置下 garden/bicycle 为负，原因在 SH 校正 |
| 下一步 | "转向估计量" | **先解决 SH 与透明度场的耦合**（这是唯一挡住收益的模块），然后再做估计量 |

## 8. SH clip 配置：所有端到端表的隐含偏差（2026-11-16 复核后发现）

### 8.1 现象与来源

本轮**所有** suite 脚本（以及历史 `suite_o2cover.sh`）都写成

```
--sh-mode dc --sh-sum 1 --sh-min-diff 0.2          # 没有显式 --sh-clip
```

于是落到 `run_o2.py` 的默认 **`--sh-clip 0.30`**。但仓库自己的结论是：

- `REPORT-sh-free.md` §5：推荐默认 **`--sh-clip 0.05`**（"三项指标全面转正的配置"）；
- `REPORT-sh-correction.md` §2.2 把 **clip=0.3** 列为"超参太猛"的失败项。

也就是说：**本轮 4 场景表、上一轮的 `REPORT-s5`/`REPORT-o2cover` 之后的复现口径，都是在一个已知不好的超参下测的。**

### 8.2 clip 扫描（同管线、同 pair 序列、只改 clip，fast 臂）

| clip | truck | room | 备注 |
|---:|---:|---:|---|
| s0（不校正） | 21.3045 | — | 基准 |
| 0.02 | 21.3331 | **27.0734** | room 最优 |
| **0.05** | 21.3632 | 27.0614 | 推荐值，两场景都在最优 0.02 dB 内 |
| 0.10 | **21.3793** | 26.9782 | truck 最优 |
| 0.20 | 21.3020 | 26.6533 | 开始崩 |
| **0.30（当前默认）** | **21.1243** | **26.2347** | 最差，甚至差于不校正 |

**结论：clip 在多场景上的最优区间是 0.02–0.10，0.05 是稳健选择；0.30 已经越过悬崖。**
相对当前默认，clip=0.05 的代价/收益（fast 臂）：

| 场景 | clip 0.30 | clip 0.05 | Δ |
|---|---:|---:|---:|
| truck | 21.1243 | 21.3632 | **+0.239** |
| room | 26.2347 | 27.0614 | **+0.827** |
| garden | 21.3479 | 22.1133 | **+0.765** |
| bicycle | 20.6589 | 20.8350 | **+0.176** |

**这个杠杆比本轮所有相机/配对改动大 3–10 倍**（相机改动的幅度是 +0.06~+0.23 dB）。

### 8.3 对相机结论的影响：四个场景全部转正

`--sh-clip 0.05`、其余不变（B=8，固定 pair 序列，同最终高斯数）：

| 场景 | fast | guard8 | track8 | cover8 |
|---|---:|---:|---:|---:|
| truck | 21.3632 | **+0.178** | +0.190 | **+0.191** |
| room | 27.0614 | +0.229 | **+0.231** | +0.218 |
| garden | 22.1133 | +0.063 | +0.039 | **+0.057** |
| bicycle | 20.8350 | +0.122 | — | **+0.198** |
| 四场景均值 | — | +0.148 | +0.153（3 场景） | **+0.166** |

- **没有一个场景是负的**：上一轮的 garden −0.125 / bicycle −0.162 完全是 clip=0.30 造成的；
- 排序：cover ≳ track ≳ guard > fast。三者差距在 0.02–0.08 dB，属于该评测器的分辨带；
- `track`（离线 `E_alpha` 最优，0.020–0.027）依然不是端到端最优，但差距已缩到 0.01–0.02 dB。

### 8.4 修订后的判定

| 项 | 上一轮 | 本轮（clip=0.05） |
|---|---|---|
| 相机选择是否有效 | "garden/bicycle 负，不建议采纳" | ✅ **4/4 场景为正**，+0.06~+0.23 dB |
| 最优臂 | cover | cover ≈ track ≈ guard（差 0.02–0.08，都在噪声带） |
| 成本 | guard +4.6~8.8% | 不变 |
| 离线 `E_alpha` 的方向 | "反相关" | ✅ 与端到端同向（差距缩小） |
| 最大杠杆 | 相机（+0.06~0.23） | **SH clip（+0.18~0.83）** |

**方法教训（应写进项目规范）：** 消融必须在调好的超参下做。本轮先后两次"负结果"
（garden −0.125、bicycle −0.162）都是把 `--sh-clip` 的默认值当成"环境"而不是"变量"造成的；
第一次归因于"全相机解不是好目标"，第二次归因于"SH 求和与视角集耦合"——**两次都错**，
正确原因是 clip 越界。可复现的检查方式：任何改动前后先跑一次 `clip ∈ {0.02, 0.05, 0.30}` 的三角验证。

## 12. 方案剩余条目 + 一个必须更正的 bug

### 12.1 更正：`track` 选择的冗余累加写错，所有旧 track 端到端数字作废

`pics.select(strategy="track")` 里累加冗余的那行原来写成

```python
red = torch.where(used, torch.maximum(red, self.M[i]), red)   # 错
```

`used` 是 (pair, camera) 的元素级掩码，于是**只有刚被选中那一列拿到惩罚，其余相机的冗余度被清零**，
惩罚在下一步完全不起作用。合成用例（`M[0,1]=0.9`、q 全 1）直接复现：应当选 `[0,2]`，实际选 `[0,1]`。
参考实现（逐候选显式循环）与 **numpy 版 `o2eval2.pair_track_greedy` 一致**，即**离线数字是对的、端到端的错了**。

修法：改成按 pair 整行更新

```python
red[rows] = torch.maximum(red[rows], self.M[i[rows]].to(red.dtype))
```

验证：合成用例 → `[0,2]` ✓；真实数据上 numpy 与 torch 的选择**集合一致率 100%**（修前只有 6.6%）。

**影响范围**：所有带 `--o2-pick track` 的端到端结果（§2.1、§4.1、§8.3 里的 track 行）都是"伪 track"（实际接近 `sup`），
作废；`camera-support-diagnostic.md` 里的离线 `p_track`（0.020/0.035/0.027/0.026）**不受影响**。

**重测（终版配置 clip .05 + p2c1 + σ1.25，B=8）：**

| 场景 | cover8（对照） | **track8（修正后）** | Δ |
|---|---:|---:|---:|
| truck | 21.5786 | 21.5731 | −0.006 |
| room | 27.3178 | **27.3556** | **+0.038** |
| garden | 22.1926 | **22.2004** | **+0.008** |
| bicycle | 21.0511 | **21.0706** | **+0.020** |

- **track 现在是 4 个场景里 3 个最优的相机臂**（均值 +0.015），与离线 `E_alpha` 的排序**方向一致**；
  §4.1 里"离线最好、端到端最差"的矛盾**是那个 bug 造成的，不是真实现象**。
- 代价：track 每对平均用 7.8 个有效视角（cover 约 3.1），O2 阶段约 **2–3×**，
  所以它适合"离线出最终结果"，而 `cover` 仍是性价比最优的默认。

- **τ ≤ 0.05 时停止准则形同虚设**：残差在 8 个视角后仍以 >5% 的步长下降，规则一路用满 10–11 个视角；
- 只有 τ=0.10 才把预算压到 8.7–9.9（省 10–20%），但 `E_alpha` 同时变差（如 truck 0.0285 → 0.0299）；

### 12.6 §21.1 选择质量指标（离线，B=8，4 场景）

| 规则 | 轨迹分布误差 ↓ | 选中集平均 track 冗余 ↓ | 跨 pair 稳定性（Jaccard） | 相机池使用率 |
|---|---:|---:|---:|---:|
| fast（固定 8） | 0.38–0.40 | 0.024–0.046 | 1.00 | 4–7% |
| cover（固定 8） | **0.60–1.40（最差）** | 0.010–0.057 | 1.00 | 4–7% |
| sup | 0.96–1.42 | 0.117–0.357（最高） | 0.12–0.22 | 40–71% |
| strat | **0.13–0.40（最好）** | 0.097–0.174 | 0.07–0.16 | 88–100% |
| guard | 0.30–0.34 | 0.036–0.066 | **0.62–0.69** | 45–65% |
| **track** | 0.29–0.59 | 0.078–0.120 | 0.05–0.10（最自适应） | 98–100% |

三项需要说明：
1. **"轨迹分布误差"与画质无关**：cover 的轨迹代表性最差（0.60–1.40）却是最好的相机臂之一；
   strat 最代表轨迹却不如 cover。这否掉了方案 §21.1 里"轨迹分布误差应作为选择质量指标"的假设。

   稳定性低不代表不好，但它意味着**换一批 pair 就会选到另一组相机**，需要用 §12.4 的方式验证泛化。

### 16.7 修订后的结论

1. **在"零训练"这个对等口径下，本方案质量最好**：ρ=0.10 时比 REFINE 高 **+5.2（truck）/ +5.9（room）** dB、

2. **速度上不是最快**：REFINE 0.7 s 比亚秒级更快（快 ~10×），我们 4–8 s，PUP 约 40–60 s。
   所以准确定位是"**同类里质量最好的秒级方法**"，而不是"唯一快速的方法"。
3. **PUP 的 +1.3~2.6 dB 是 5000 步微调买来的**（约 3 min，比我们慢 20–40×）；
   PUP 一旦不做微调，10% 保留率只剩 14.76 dB——说明**纯剪枝准则本身在低保留率下都撑不住**，

4. 这也解释了 §16.2 的规律：保留率越低，需要"重新拟合"的幅度越大，我们的相对优势才越大。

| PUP + 5k 微调 | ~50 s | ~150 s | **~200 s** | 26–48× |

**结论：给 REFINE 补 5000 步微调要 1.4–2.6 分钟**（10%–50% 保留率），即本方案全流程的 **11–37 倍**；
换来 k10 +7.2 dB、k50 +1.7 dB。加上微调后 REFINE 是这一档最强的（k10 23.56 > PUP+FT 22.93 > 本方案 21.58），
所以公平的定位是：**本方案在"零训练"里质量最好、速度快 10–30×；若对手允许分钟级微调，则约落后 2 dB。**

> 踩坑记录：在同一 shell 里跑完 PUP 训练再评测，会因 `PYTHONPATH` 里残留 PUP 的
> `diff_gaussian_rasterization` 而报 `GaussianRasterizationSettings got an unexpected keyword
> argument 'antialiasing'`，渲染失败 → 指标 NaN。评测务必在干净环境里跑。

### 16.9 极端压缩率（ρ=0.5 / 0.01）下重测当年被省掉的选边/共面准则

动机：ρ=0.5 与 ρ=0.01 上本方案与其他方法几乎没有差距，因此"选边/共面判据"这类
**在高 ρ 时被证明有效但幅度太小**的模块，可能在极端压缩率下才显出作用。
所有代价项在代码里都按自身均值归一化，因此权重 0.5/1.0 与 p2c1 的 (plane 2.0, cg 1.0) 同量级。

**ρ = 0.50（truck，1,027,857 高斯）：全部打平，噪声级 0.002 dB**

| 变体 | PSNR | Δ vs base |
|---|---:|---:|
| base（p2c1） | 23.6206 | — |
| e4 | 23.6207 | +0.0001 |
| ax10（cost-axis 1.0） | 23.6206 | 0.0000 |
| n05（cost-normal 0.5） | 23.6204 | −0.0002 |
| n10（cost-normal 1.0） | 23.6202 | −0.0004 |
| plain（去掉 p2c1） | 23.6201 | −0.0005 |
| sr10（cost-sratio 1.0） | 23.6198 | −0.0008 |
| maha_fast（scorer） | 23.6189 | −0.0017 |
| kl（scorer） | 23.6187 | −0.0019 |

→ **ρ=0.5 时选边策略完全无效**：连"把 p2c1 整个删掉"也只掉 0.0005 dB。
原因很直接：只合并一半时，每个合并只吞 2 个高斯、证据充足，代价函数怎么排都不影响结果。

**ρ = 0.01（truck，20,558 高斯）：差异放大 100 倍（0.22 dB），轴向项最好**

| 变体 | PSNR | Δ vs base | SSIM | LPIPS |
|---|---:|---:|---:|---:|
| **ax10（cost-axis 1.0）** | **18.5087** | **+0.054** | 0.56184 | 0.54042 |
| n05 | 18.4810 | +0.026 | 0.56173 | 0.53991 |
| plain（去掉 p2c1） | 18.4802 | +0.025 | 0.56004 | 0.54385 |
| e4 | 18.4745 | +0.019 | 0.56332 | 0.54038 |
| base | 18.4551 | — | 0.56237 | 0.54031 |
| n10 | 18.4481 | −0.007 | 0.56160 | 0.54135 |
| maha_fast | 18.4118 | −0.043 | **0.56679** | **0.52519** |
| sr10 | 18.3453 | −0.110 | 0.55985 | 0.54188 |
| kl | 18.2853 | −0.170 | 0.56109 | 0.53708 |

- **`--cost-axis 1.0` 在 1% 上确实有效**（+0.054），且 `pure scale_norm` 也略好于 p2c1（+0.025），
  说明**低保留率下"平面/共视"项的相对价值下降、轴向对齐的相对价值上升**；
- 历史默认的 `kl` 在两个极端都是最差的（−0.17），`cost-sratio` 也明确有害；
- `maha_fast` 的 PSNR 低 0.043 但 **SSIM +0.0044、LPIPS −0.015** 都是最好，属于指标权衡而非变差。

**room @ ρ=0.01 复现（+0.201 dB）**

| 变体 | PSNR | SSIM | LPIPS |
|---|---:|---:|---:|
| base | 22.6737 | 0.73003 | 0.48653 |
| **ax10** | **22.8749** | 0.72934 | 0.48563 |

→ 轴向项的收益在 room 上更大（+0.201），方向一致。

**ρ=0.01 时本方案与 REFINE 的差距**

| 场景 | 本方案（1%） | REFINE（1%，零训练） | Δ |
|---|---:|---:|---:|
| truck | **18.4551** | 11.6870 | **+6.77** |
| room | **22.6737** | 14.7994 | **+7.87** |

**结论（回答"极端压缩率下老方法能否发挥"）：**

1. **ρ=0.5：不能。** 选边/共面/轴向/scorer 全部落在 0.002 dB 内，做任何调参都是浪费；
   这一档本方案与对手打平的根本原因是"合并得太轻"，不是"判据不够好"。
2. **ρ=0.01：能，但幅度有限。** 差异从 0.002 放大到 0.22 dB，`--cost-axis 1.0` 是唯一稳定的正收益
   （truck +0.054、room +0.201，SSIM/LPIPS 基本不变）。建议**只在 ρ ≤ 0.02 时开启**
   （高 ρ 下中性、零成本），并避免 `kl` / `cost-sratio`。
3. **真正的差距仍在"重拟合"而不是"选边"**：1% 时本方案比 REFINE 高 6.8–7.9 dB，
   远大于选边能带来的 0.05–0.20 dB。选边是锦上添花，O2cal 才是量级来源。
